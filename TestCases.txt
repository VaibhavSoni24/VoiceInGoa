## Test Case 1 — Straightforward grounded query (happy path)

**Input (spoken, Hindi or English depending on what you tested with Sarvam):**
"भारत की राजधानी क्या है?" / "What is the capital of India?" *(or any question you know is well-covered in your MS MARCO-XI subset)*

**Expected pipeline behavior:**
1. Sarvam STT returns transcribed text with high confidence
2. Query embedded via `multilingual-e5-small`
3. Qdrant returns top-3 passages, top similarity score ≥ 0.75
4. Grounding guardrail passes (score above threshold)
5. `mercury-2` generates answer citing the retrieved passage(s)
6. Post-generation grounding check confirms answer content overlaps with cited passage

**Expected output:**
```json
{
  "status": "answered",
  "transcribed_query": "What is the capital of India?",
  "answer": "New Delhi is the capital of India.",
  "confidence_score": 0.89,
  "citations": [
    {"passage_id": "msmarco_xi_00421", "similarity": 0.89, "snippet": "...New Delhi serves as the capital..."}
  ],
  "guardrail_triggered": null,
  "latency_ms": {"stt": "excluded", "retrieval": 38, "generation": 71, "total": 119}
}
```
UI should show: the answer text, a visible citation/source link, and latency numbers on screen.

## Test Case 2 — Off-topic query (guardrail should trigger before generation)

**Input:** "What's the weather like in Goa tomorrow?" *(assuming your MS MARCO-XI subset has no weather-forecast content)*

**Expected pipeline behavior:**
1. STT transcribes correctly
2. Retrieval runs, but top similarity score falls **below 0.75**
3. Grounding-confidence guardrail intercepts *before* the query reaches `mercury-2` (saves a generation call — worth calling this out in your demo as an efficiency choice, not just a safety one)
4. System returns a refusal, not a hallucinated guess

**Expected output:**
```json
{
  "status": "refused",
  "transcribed_query": "What's the weather like in Goa tomorrow?",
  "answer": null,
  "confidence_score": 0.31,
  "citations": [],
  "guardrail_triggered": "low_retrieval_confidence",
  "message": "I don't have enough grounded information in my knowledge base to answer that confidently.",
  "latency_ms": {"retrieval": 35, "generation": 0, "total": 40}
}
```
**Why this test matters for judges:** proves the guardrail fires on *retrieval* confidence, not just on the LLM "deciding" to refuse — a stronger engineering claim.

## Test Case 3 — Unsafe/inappropriate input

**Input:** Any deliberately harmful or clearly inappropriate spoken request (pick something mild and obviously off-limits for a live demo — avoid anything genuinely graphic in front of judges).

**Expected pipeline behavior:**
1. STT transcribes
2. Input safety filter runs **before** retrieval/embedding (cheapest, fastest stage to reject at)
3. Query never reaches vector DB or LLM

**Expected output:**
```json
{
  "status": "refused",
  "transcribed_query": "<transcribed unsafe text>",
  "answer": null,
  "guardrail_triggered": "unsafe_input_filter",
  "message": "I can't help with that request.",
  "latency_ms": {"input_filter": 4, "retrieval": 0, "generation": 0, "total": 4}
}
```
**Why this test matters:** shows the guardrail short-circuits early — good evidence for your "harness with proper error/edge-case handling" claim, and it's your fastest response of all test cases (worth highlighting).

## Test Case 4 — Ambiguous query near the threshold (edge case)

**Input:** A query that's topically adjacent to your corpus but not directly answerable — e.g., asks about a related-but-not-covered entity, expected to land retrieval similarity right around 0.70–0.78.

**Expected pipeline behavior:**
This is your **hardest and most valuable test to show live** — it demonstrates the threshold is a real, working number rather than decorative. Run it twice if your first attempt lands just above threshold and just below on a repeat, to show the boundary behavior explicitly.

**Expected output (if below 0.75):**
```json
{
  "status": "refused",
  "confidence_score": 0.71,
  "guardrail_triggered": "low_retrieval_confidence",
  "message": "I don't have enough grounded information..."
}
```
**Expected output (if above 0.75):**
```json
{
  "status": "answered",
  "confidence_score": 0.77,
  "answer": "...",
  "citations": [...]
}
```
Document both outcomes in your demo video narration — "here's what happens right at the edge of our confidence threshold."

## Test Case 5 — Post-generation hallucination catch (grounding check works even when retrieval succeeds)

**Input:** A query where retrieval succeeds (passes 0.75) but is deliberately phrased to tempt the LLM into adding unsupported detail (e.g., asks a follow-up "and why?" when the retrieved passage states a fact but not a reason).

**Expected pipeline behavior:**
1. Retrieval passes threshold
2. `mercury-2` generates an answer
3. Post-generation grounding guardrail checks the answer's claims against retrieved passage content
4. If the model added unsupported reasoning, the guardrail should either strip the unsupported claim, flag it, or trigger a refusal/regeneration — whichever your implementation does

**Expected output (example: guardrail flags and trims):**
```json
{
  "status": "answered_partial",
  "answer": "New Delhi is the capital of India.",
  "guardrail_triggered": "unsupported_claim_removed",
  "note": "Additional reasoning was removed because it was not supported by retrieved context.",
  "citations": [{"passage_id": "msmarco_xi_00421", "similarity": 0.89}]
}
```
**Why this test matters:** this is the single most impressive test to show judges — it proves your grounding check operates on the *output*, not just the input/retrieval, which is what separates "guardrails" from "just a similarity threshold."

## Test Case 6 — Retry/error-recovery under simulated failure (harness stress test)

**Setup:** Kill network access briefly, or temporarily invalidate the Sarvam or InceptionAPI key, mid-demo.

**Expected pipeline behavior:**
1. `tenacity`-wrapped call fails
2. Retry fires (with backoff) 2–3 times as configured
3. If all retries exhausted, pipeline returns a **clean, typed failure** — not a raw stack trace or hung request
4. Timeout doesn't hang the UI indefinitely

**Expected output:**
```json
{
  "status": "error",
  "error_type": "upstream_service_failure",
  "service": "sarvam_stt",
  "retries_attempted": 3,
  "message": "Voice transcription service is temporarily unavailable. Please try again.",
  "latency_ms": {"total": 4200}
}
```
**Why this test matters:** directly demonstrates "structured orchestration... retries, structured input/output handling, error recovery" from the rubric — do this one on camera deliberately, it's otherwise invisible if everything just works.
